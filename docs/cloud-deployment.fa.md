# فازهای ۴ و ۵ — ذخیره‌سازی ابری و استقرار خصوصی

[English](./cloud-deployment.md)

## چه چیزی پیاده‌سازی شده است؟

- انتخاب مخزن حافظه‌ای یا `Firestore` برای اجرای همان جریان پرونده.
- ثبت اتمیک اطلاعات پرونده، فیلدها، بررسی انسانی و تاریخچه در `cases/{id}`. اطلاعات در فیلد `payload` به‌شکل JSON ذخیره می‌شوند؛ بایت‌های سند داخل دیتابیس نمی‌روند.
- ذخیرهٔ اصل PDF یا تصویر در `Cloud Storage` یا پوشهٔ محلی.
- آپلود و دانلود اصل سند از رابط کاربری. فایل‌ها خصوصی می‌مانند.
- کنترل نوع فایل و امضای اولیهٔ PDF، JPEG و PNG، با حداکثر حجم ۵ MiB. این کنترل‌ها جایگزین اسکن بدافزار نیستند.
- تراکنش برای جلوگیری از حذف تغییرات هم‌زمان کاربران.
- ساخت یک container برای Frontend و Backend و استقرار خصوصی روی `Cloud Run`.
- مسیر `/health` برای سلامت برنامه و `/ready` برای بررسی دسترسی ذخیره‌سازی.

مدل همچنان `mock` است؛ خروجی آن از فایل آپلودشده استخراج نمی‌شود. اتصال واقعی Gemini در فاز ۶ انجام می‌شود. رابط این محدودیت را نمایش می‌دهد.

## وضعیت واقعی

کد و تست‌های محلی آماده‌اند. CI برای ساخت Docker و آزمایش Firestore Emulator تنظیم شده است. تا اجرای موفق روی پروژهٔ واقعی و تأیید ماندگاری پرونده بعد از تغییر revision، فازهای ۴ و ۵ از نظر عملیاتی بسته نیستند.

منابعی که طبق تأیید امین قبلاً ایجاد شده‌اند:

| منبع | نام |
|---|---|
| پروژه | `claimflow-ai-agents` |
| منطقه | `australia-southeast1` |
| دیتابیس | `(default)` |
| Bucket | `claimflow-ai-agents-documents` |
| Artifact Registry | `claimflow-containers` |
| هویت اجرا | `claimflow-api-runtime@claimflow-ai-agents.iam.gserviceaccount.com` |

هویت اجرای Cloud Build با هویت Runtime فرق دارد. دسترسی واقعی ساخت و deploy هنوز تأیید نشده است. اسکریپت در اولین خطای دسترسی متوقف می‌شود؛ در صورت خطا، همان پیام غیرحساس را بررسی می‌کنیم.

## اجرا روی Windows

ابتدا dev server قبلی را با `Ctrl+C` متوقف کن. پس از merge شدن PR:

```powershell
git switch main
git pull origin main
npm ci
npm run typecheck
npm test
npm run build
.\scripts\deploy-cloud.ps1
```

اسکریپت منابع موجود را بررسی می‌کند، تصویر را با شناسهٔ commit می‌سازد و سرویس خصوصی را با صفر instance حداقلی و حداکثر یک instance مستقر می‌کند. ساخت و ذخیره‌سازی می‌توانند هزینه داشته باشند؛ سقف instance سقف هزینه نیست. کلید Service Account ساخته نمی‌شود.

سپس در یک Terminal جدا:

```powershell
gcloud run services proxy claimflow-api --project=claimflow-ai-agents --region=australia-southeast1 --port=8081
```

و در Terminal دیگر:

```powershell
node scripts/smoke.mjs http://localhost:8081
```

مرورگر را در `http://localhost:8081` باز کن. تست، ساخت پرونده، آپلود، مقایسهٔ بایت‌های فایل دانلودی، processing، review و چهار audit event را بررسی می‌کند. آدرس سند در حالت ابری باید با `gs://claimflow-ai-agents-documents/` شروع شود.

برای بستن فاز ۵، همان تصویر را در revision جدید اجرا کن و دوباره پروندهٔ چاپ‌شده توسط تست و اصل فایل را دریافت کن. اطلاعات باید همچنان موجود باشند. نتیجهٔ تست و نام revision را ثبت می‌کنیم.

## محدودیت‌های مشخص

- سقف اطلاعات هر پرونده ۷۰۰ KB است و فهرست ابری فقط ۱۰۰ پروندهٔ اخیر را نمایش می‌دهد. تقسیم تاریخچه به subcollection و pagination برای مقیاس بعدی است.
- در حالت محلی، بایت فایل باقی می‌ماند اما اطلاعات پرونده با Restart حافظه از بین می‌رود.
- فایل `.env.example` راهنماست؛ فرمان فعلی سرور فایل `.env` را خودکار بارگذاری نمی‌کند. تنظیمات را از متغیرهای محیطی می‌خواند.
- دسترسی Cloud Run کل محیط آزمایشی مشترک را محافظت می‌کند؛ جداسازی پرونده‌ها بر اساس کاربر هنوز وجود ندارد. نام reviewer نیز برچسب ارسالی کاربر است.
- اگر آپلود موفق شود ولی ثبت دیتابیس خطا بدهد، فایل برای بررسی نگه داشته و مسیر آن در log ثبت می‌شود. به‌دلیل احتمال ثبت موفق تراکنش باوجود timeout، حذف خودکار فایل خطرناک است. پاک‌سازی فایل‌های بی‌مرجع و جلوگیری از آپلود تکراری هنوز خودکار نیست.
- Behzad برای تست نهایی از هویت Google خودش و دسترسی `Cloud Run Invoker` استفاده می‌کند.

جزئیات IAM، بازگردانی revision و منابع رسمی در راهنمای انگلیسی آمده است.
